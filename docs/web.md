# Web app

The Next.js frontend in `web/`: the chat page, the projects list and project pages, the requests list and detail
pages, and the admin Users page, where admins invite colleagues ([the invite flow](auth-setup.md#inviting-users)).

## Running it

To run it in Docker with the rest of the app, see [local-development.md](local-development.md); the image is built by
`web/Dockerfile`. To work on it, from `web/`, with Node 22 and Corepack enabled (`corepack enable`), so you get the npm
version pinned in `package.json`:

Copy `.env.example` to `.env.local` and fill in `AUTH_SECRET` and `AUTH_KEYCLOAK_SECRET` first (see
[auth-setup.md](auth-setup.md#client-secrets)). Every page needs sign-in, so start Keycloak (`docker compose up -d` from
the repo root) and, for anything that calls the API, the API too.

```bash
npm install          # also installs the Husky pre-commit hook
npm run dev          # http://localhost:3000
npm run lint         # ESLint, including Prettier and import order
npm run format       # Prettier --write
npm test             # Vitest, once
npm run build        # production build to .next/standalone
```

The pre-commit hook runs `lint-staged`: `eslint --fix` on staged TS/JS files and Prettier on JSON, CSS and Markdown.

## Sign-in and the session

Auth.js v5 signs users in with Keycloak; [auth-setup.md](auth-setup.md#how-the-web-app-signs-in) has the details.
For code in `web/`:

- **The current user:** in a Server Component, `await getCurrentUser()` from `lib/auth/session.ts` returns
  `{ id, name, email, isAdmin }` or null. It reads cookies, so with Cache Components the component that calls it has
  to sit behind a `<Suspense>` boundary, as `SessionHeaderNav` does in `AppShell`. Keep the read out of layouts'
  top level, or the whole page waits for it. Pass this narrow user to Client Components, never the session.
- **Admin-only UI:** use `user.isAdmin` to hide links and controls. For a whole admin page, wrap its content in
  `<AdminOnly>` (`components/admin/admin-only.tsx`) inside a `<Suspense>` boundary: it reads the session and
  redirects anyone who isn't an admin to `/chat`. Both only keep the UI tidy; the API enforces `rp-admin` itself.
- **Calling the API from the browser:** fetch `/api/proxy/<path>`, which goes to `<API_URL>/api/<path>` with the
  user's access token. A signed-out request gets 401. Responses stream, so server-sent events work through it.
  Use `apiFetch` from `lib/api.ts`, and wrap the calls in TanStack Query hooks (`useQuery` to read, `useMutation` and
  invalidate the list's query key to change), as `components/admin/use-invitations.ts` does. The API's errors are
  problem details; `apiFetch` throws them as an `ApiError` whose message is fit for a toast.
- **URL hooks on dynamic routes:** with Cache Components, `usePathname`, `useParams` and `useSearchParams` suspend on
  a route with a dynamic segment (such as `/chat/[id]`), and anything in a layout above it suspends too. Render the
  component that calls them inside a `<Suspense>` boundary whose fallback doesn't call them, as `HeaderNav` does with
  `MainNav` / `MainNavLinks`, or the build fails.
- **Sign in and out:** `signInWithKeycloak` and `signOutEverywhere` in `lib/auth/actions.ts` are server actions.

## The chat page

`/chat` lists the user's conversations (`ConversationList`, beside every chat page) and offers **New conversation**,
which creates one (`POST /api/conversations`) and opens `/chat/<id>`. The conversation page loads its messages
(`GET /api/conversations/<id>`) into `ChatThread`, which owns them from then on.

Sending a message calls `sendMessage` in `lib/chat.ts`: a `fetch` POST through the proxy whose response body is read as
it arrives and parsed by `SseParser` ([the events](agent.md#post-apiconversationsidmessages)). `text` events append to
the reply as it's written; each `proposal` event adds a `ProposalCard`; `error` ends the reply with its message under
it, keeping whatever text had arrived. A message the API refuses outright (429 over the rate limit, 403, 404) is taken
back out of the thread and put back in the box, with a plain explanation of the rate limit.

Assistant text is Markdown, rendered by `Markdown` with `remark-gfm` and `rehype-sanitize`; raw HTML is never rendered.

`ProposalCard` shows the proposal's type, its variables (labels from the manifest), the **Project** it goes in, linking
to the project page (left out on a `project` request's own card, whose name is already in the table), and its cost
hint. It reads the
request's current status (`GET /api/requests/<id>`), so an old proposal shows where it got to. While it awaits
confirmation, **Confirm** and **Cancel** call `POST /api/requests/<id>/confirm` or `/cancel`. Confirming shows a toast
with a **View request** action and swaps the buttons for a link to the request page. Cancelling deletes the request
(the API answers 204), so the card re-reads it, gets 404 and says **No longer exists**, with no buttons or link; so
does any card whose request has been cancelled or destroyed since. Errors show on the card and in a
toast; over an active-request limit, the card explains it under "You're at your limit" with the API's advice. A
proposal that references others says **Runs after** with links to them; confirming it before them is refused by the API
with a message saying which to confirm first.

When a reply has two or more proposals still awaiting confirmation, `ConfirmAllButton` offers **Confirm all (N)**,
which calls `POST /api/requests/confirm` with their IDs: the API checks the spend limits for all of them and queues
them in dependency order, or confirms none. It reads the statuses from the same queries as the cards, so both update
together, and leaves out any that no longer exist.

## The projects pages

Every resource belongs to one project ([how projects work](architecture.md#projects)), so resources are browsed by
project.

- **`/projects`** lists the user's projects (everyone's for an admin, with an **Owner** column) from
  `GET /api/projects`: name (linking to the project), status, environment, how many resources are in it, and when it
  was created. A project's status is that of the `project` request that backs it. The list re-reads itself every 3
  seconds while a project is being created or destroyed (`useProjects`).
- **New project** opens a dialog whose form is built from the `project` type's manifest (`GET /api/catalog`): a field
  for each plain string variable, with its label, description and default, and a select where it has allowed values.
  `variablesSchema` in `lib/projects.ts` turns the manifest's rules (required, `maxLength`, `pattern`,
  `allowedValues`) into a zod schema for react-hook-form; the API checks them again. Secrets and variables that
  reference other requests are never fields. Submitting calls `POST /api/projects`, which proposes and confirms the
  project in one step (the submit is the confirmation), sending only the fields that were filled in so the API
  applies the other defaults; it then opens the new project's page. The API's errors show in the dialog.
- **`/projects/<id>`** (`GET /api/projects/<id>`) shows the project's status, its settings (description, purpose,
  environment) with a link to its `project` request (for the log and outputs), and its **Resources**: each links to its
  request page, with its status, and anything that depends on another resource in the project is indented under it
  (`resourceTree`; under the first one if it depends on several, with "also needs" naming the rest). The owner gets
  **Start a chat**, which starts a conversation to ask for more. The page re-reads itself while anything in it has a
  job queued or running (`useProject`). The header's actions are where **Delete project** will go. A project that
  was there and then answers 404 (its `project` request was destroyed or cancelled) toasts and goes to `/projects`;
  one that never was says it doesn't exist.

## The requests pages

`/requests` lists the user's requests (everyone's for an admin, with an **Owner** column) in a TanStack Table: type
(linking to the request), name, project (linking to it), status and when it was created. The **Project** select above
it filters the list to one project's requests and the `project` request that backs it. The filter lives in the URL
(`/requests?project=<id>`), which the page reads from its `searchParams` behind the same `<Suspense>` as the session,
and filters the shared list query in the browser. `/requests/<id>` shows one request: its status, the project it's in
(or, for a `project` request, the one it backs), the settings it was created with, its outputs (described from the
catalog), the Terraform log, and **Destroy**. A request
that references others, or that others reference, shows them under **Related requests** (**Depends on**, **Needed
by**), with their statuses. While queued, it says what it's **waiting for**. While something that depends on it may
still exist, Destroy is replaced by the requests to destroy first.

- **Status** shows as a `StatusBadge`, with a spinner while a job is queued or running. The list and the request
  re-read themselves every 3 seconds while a job is in progress (`useRequests` / `useRequest`), and the chat's proposal
  cards share the same queries.
- **The log** streams from `GET /api/requests/<id>/logs` ([the events](provisioning.md#get-apirequestsidlogs)) through
  `followLogs`. Each `status` event refreshes the request. When a job starts (after Destroy, say), the stream reconnects
  with `Last-Event-ID` and carries on below the earlier lines.
- **Secret outputs** (passwords, keys, connection URIs) are shown to the owner only, masked until they click **Reveal
  secrets**, which is the only time `GET /api/requests/<id>/sensitive-outputs` is called. **Hide secrets** drops them
  from the query cache, and the response is never cached by the browser.
- **Destroy** is offered to the owner or an admin once the request is Provisioned or Failed. It asks for confirmation
  in an alert dialog, then the badge and the log follow the destroy. Once it's destroyed, the API deletes the request:
  the log stream ends with a `deleted` event, the page re-reads the request and gets 404, and since it had the request
  before, it toasts "… was destroyed" and, with `router.replace`, goes to its project's page; to `/projects` for a
  `project` request, whose project went with it; and to `/requests` for a request with no project.
- **Lists never show cancelled or destroyed requests**, which the API deletes, and `StatusBadge` has no state for them.
  A request the user opens that was already gone, or was never theirs, says it doesn't exist.
- A request or conversation the user can't see (404) isn't retried: `retryUnlessClientError` retries only server and
  network errors. `isNotFound` in `lib/api.ts` tells a 404 apart.

## Stack

| Concern | Library | Notes |
| --- | --- | --- |
| Framework | `next` 16, `react` 19, TypeScript | App Router, `output: 'standalone'`, Cache Components on |
| Auth | `next-auth` v5 (Auth.js), Keycloak provider | JWT sessions in an encrypted cookie |
| Styling | `tailwindcss` v4 via `@tailwindcss/postcss`, `tw-animate-css` | theme tokens in `app/globals.css` |
| Components | `shadcn` CLI, style `base-nova` (`@base-ui/react`), `class-variance-authority`, `cn` | `cn` replaces `clsx` + `tailwind-merge` in current shadcn |
| Icons | `lucide-react` | the only icon set |
| Theme | `next-themes` | class-based dark mode |
| Forms | `react-hook-form` + `zod` + `@hookform/resolvers`, shadcn `field` | `base-nova` has no `form` component |
| Tables | `@tanstack/react-table` | shadcn data-table pattern |
| Toasts | `sonner` | `toast()` from anywhere |
| Chat text | `react-markdown` + `remark-gfm` + `rehype-sanitize` | never `rehype-raw`: assistant output is untrusted |
| Client data | `@tanstack/react-query` | polling, mutations, cache invalidation |
| Tests | `vitest`, Testing Library, `jsdom`, `@vitejs/plugin-react` | colocated `*.test.tsx` |
| Lint and format | `eslint` + `eslint-config-next`, `prettier`, `eslint-plugin-simple-import-sort`, `husky` + `lint-staged` | |

Left out on purpose: milkdown, cmdk, motion, nuqs, react-icons.

## shadcn components

Installed: alert-dialog, avatar, badge, button, card, dialog, dropdown-menu, field, input, label, scroll-area, select,
separator, skeleton, sonner, table, tabs, textarea and tooltip. Add more with `npx shadcn@latest add <name>` from
`web/`.

Base UI components compose through the `render` prop rather than Radix's `asChild`:

```tsx
<DropdownMenuTrigger render={<Button variant="ghost" size="icon" />}>…</DropdownMenuTrigger>
```
