# Agent

The chat agent works out which catalog resource the user wants, asks for whatever is missing, and proposes a request
for the user to confirm. It lives in `api/src/ResourceProvisioner.Api/Services/Agent/`. It never writes Terraform and
never starts provisioning: `propose_request` only creates a request in `AwaitingConfirmation`, and only the user's
Confirm click (`POST /api/requests/{id}/confirm`) queues it (see [architecture.md](architecture.md#key-design-rules)).

## How a message is answered

```
POST /api/conversations/{id}/messages ─▶ save the user's message
   ┌──────────────────────────────────────────────────────────────┐
   ▼                                                              │
 Claude (streamed): text deltas ─▶ SSE `text` events              │
   │ stop_reason                                                  │
   ├─ end_turn ─▶ save the reply ─▶ `done`                        │
   ├─ tool_use ─▶ save the reply, run the tools on the server,    │
   │              save the results ─▶ `proposal` per request ─────┘  (at most 10 calls to Claude per message)
   └─ refusal / max_tokens / API error ─▶ `error` (the reply isn't saved)
```

`ChatAgent` runs a manual tool-use loop over `IChatModel`. Each call to Claude streams its text straight to the
browser. When Claude asks for tools, `AgentToolExecutor` runs them as the chatting user and their results go back in
the next call. The loop ends when Claude ends its turn, or after `ChatAgent.MaxModelCalls` (10) calls, so a model
stuck calling tools can't run up a bill.

`IChatModel` speaks the Messages API's JSON wire format, so the loop and the database never depend on SDK types.
`AnthropicChatModel` is the only class that uses the `Anthropic` NuGet package. Tests replace it with `FakeChatModel`.

### What's sent to Claude

| | |
| --- | --- |
| Model and effort | `Anthropic:Model` (default `claude-sonnet-5-5`) at `output_config.effort` = `Anthropic:Effort` (default `low`, enough for a short conversation and cheap). Thinking is left at the model's default (adaptive). |
| Endpoint | The beta Messages endpoint, for **server-side refusal fallback**: `fallbacks: "default"` with the `server-side-fallback-2026-07-01` beta. When Sonnet 5.5 declines in a category the server can retry (`cyber`, `frontier_llm`), it retries the turn on Claude Sonnet 5 instead of refusing. Firewall and database rules can look like security work, so this matters here. |
| Caching | Top-level `cache_control` (automatic prompt caching): the tools and system prompt are fixed, and the history only grows, so every turn after the first reads the earlier turns from cache. |
| Tools | The [four tools](#tools): three `strict: true`, `propose_request` not (see below). |
| `max_tokens` | 16,000. Replies are short; this is a ceiling, not a cost. |

## System prompt

`SystemPrompt.Text` is fixed text (nothing per-user or per-catalog is in it, so it caches). Its intent:

- Pick a type from `list_resource_types` only; if nothing fits, say so. Never invent a type.
- Read the type's spec before discussing settings, and trust it over general DigitalOcean knowledge.
- Ask only for what's missing or ambiguous, one or two questions at a time; use defaults and mention them.
- Put everything but a project in one of the user's [projects](architecture.md#projects), as `propose_request`'s
  `project_id`, found with `list_my_resources`: the only one, or ask which if there are several. With none, offer to
  propose one first. A project proposed earlier in the same reply can be used at once, so "a project with a droplet
  in it" is one reply.
- Reference the user's existing droplets by request ID, via `list_my_resources`.
- For resources that build on each other (a droplet and a firewall on it), propose them in one reply, the one needed
  first, referencing it by the `requestId` the first `propose_request` returned. The app provisions them in order, and
  the user can confirm them all at once.
- Call `propose_request` once everything is agreed, fix any errors it returns, then tell the user to review the card
  and click Confirm, with the cost hint. Never say something has been created.
- Never ask for or repeat secrets.

## Tools

Generated by `AgentTools.For(catalog)` from the manifests, in a fixed order. The schema mapping and its size limits
are in [catalog.md](catalog.md#mapping-to-tool-schemas).

`list_resource_types`, `get_resource_spec` and `list_my_resources` are sent with `strict: true`, so their inputs always
match. **`propose_request` isn't.** Its `variables` is an `anyOf` of every type's variables, and strict decoding
writes an object's required properties first, then commits to whichever `anyOf` branch still matches. After `name`
and `region`, only the Spaces bucket's shape fits, so a droplet's `size`, `image` and required `ssh_public_key` could
never be written. The model kept proposing droplets without a key and couldn't see why. Without strict, Claude writes
the type it means from the same schema, and the server's validation, which is the authority either way, returns any
errors by field for it to fix.

| Tool | Input | Result |
| --- | --- | --- |
| `list_resource_types` | none | `[{type, displayName, description, costHint}]` for every type |
| `get_resource_spec` | `type` (enum of the catalog's IDs) | The type's manifest without its sensitive variables: every variable's rules, `atLeastOneOf`, outputs |
| `list_my_resources` | none | The user's own requests (cancelled and destroyed ones are deleted, so never appear), grouped by project: `{"projects": [{projectId, name, status, projectRequestId, variables, outputs, createdAt, resources: [...]}], "notInAProject": [...]}`. Each resource has its request ID, type, status, variables and non-sensitive outputs; `notInAProject` holds requests from before projects, and proposals whose project was cancelled or destroyed. Only the user's own, **admins included**: the agent acts for the user. |
| `propose_request` | `type` (enum), `project_id` (string or null, required) and `variables` (`anyOf` the types' variable objects) | Calls `IProvisioningRequestService.ProposeAsync` as the user, recording the conversation ID. Invalid: `is_error` with `{"errors": {field path: [messages]}}`, for Claude to fix. Valid: `{"proposal": ..., "next": ...}`, and the browser gets a `proposal` event. A reference variable's description says which type it takes, and that pending requests (such as one proposed earlier in the reply) are fine. |

### `project_id`

Every type but `project` belongs to one of the user's [projects](architecture.md#projects), so `propose_request` takes
a top-level `project_id`. It's a tool parameter, not a manifest variable, so it isn't in any type's `variables`.

- **Required but nullable** (`"type": ["string", "null"]`), not optional: strict mode allows only 24 optional
  parameters across all strict tools, and a required one uses none of them. `propose_request` isn't strict today, but
  `AgentToolsTests.RealCatalog_StaysWithinStrictToolLimits` checks its own parameters are all required, so it would
  still fit if it were.
- **Null only for a `project`**, which belongs to no project. Otherwise it must be one of the user's own projects,
  admins included, that is pending or provisioned (not failed or being destroyed). Someone else's project and a
  missing one (including one cancelled or destroyed, and so deleted) get the same error, on `project_id`; so does a
  value that isn't a GUID.
- **A project proposed in the same reply works.** Proposing a `project` returns its new project as `proposal.project`
  and a `next` hint naming the ID to use, so "a project with a droplet in it" is two `propose_request` calls in one
  reply. The member depends on the project's request, so it's provisioned first and can't be confirmed before it;
  **Confirm all** handles both.

A tool that throws returns a generic `is_error` result (details go to the API's log), so the loop carries on.

### Secrets never reach Claude

- The DigitalOcean token and Spaces keys are never read by the agent.
- Sensitive variables are left out of the schemas and of `get_resource_spec`, so Claude can't set or see them.
- Tool results come from `ProvisioningRequestResponse`, which leaves out sensitive variables and never loads
  `RequestSensitiveOutputs`.

## Endpoints

Every endpoint requires sign-in. Users see and write in their own conversations; admins can read everyone's (list and
detail) but write only in their own, because the agent acts as the conversation's owner.

| | Owner | Another user | Admin, someone else's |
| --- | --- | --- | --- |
| `POST /api/conversations` | 201, a new empty conversation | | |
| `GET /api/conversations` | their own | their own | everyone's |
| `GET /api/conversations/{id}` | 200 | 404 | 200 |
| `POST /api/conversations/{id}/messages` | 200, an event stream | 404 | 403 |

`GET /api/conversations/{id}` returns the conversation as the chat page shows it: what the user typed, and each reply's
text (the turns of one reply, split by tool calls, joined into one message) with the proposals made in it, read back
from the stored tool results, so each has the same shape as its `proposal` event, `project` included. Tool calls,
tool results and thinking are left out. The title is the start of the first message (80 characters).

### `POST /api/conversations/{id}/messages`

Body `{"text": "..."}` (1 to 4,000 characters; 400 otherwise). The response is server-sent events:

| Event | `data` | When |
| --- | --- | --- |
| `text` | `{"text": "..."}` | each piece of the reply, as Claude writes it (Markdown) |
| `proposal` | `{"requestId", "type", "displayName", "costHint", "items": [{"name", "label", "value"}], "dependsOn": [{"id", "type", "displayName", "name", "status"}], "project": {"id", "name"}}` | each request `propose_request` created, for the confirmation card; items follow the manifest's order and labels, without sensitive variables; `dependsOn` lists what it references (its project's request included); `project` is the project it goes in, or for a `project` request the one it backs |
| `done` | `{}` | the reply is complete; the stream closes |
| `error` | `{"error": "..."}` | the reply stopped early, with a message for the user; the stream closes |

Only one reply runs at a time per conversation. A second message sent meanwhile gets an `error` event straight away,
because two interleaved replies would corrupt the history.

## Stored history

`Conversations` (owner, title, timestamps) and `ConversationMessages` (role and content blocks as wire-format JSON,
ordered by ID). Messages are **append-only**: each user message, each assistant turn and each set of tool results is
saved as it completes, and replayed unchanged on the next call. That includes `thinking` blocks with their signatures,
which Claude Sonnet 5.5 binds to the exact history before them, so editing an earlier message would invalidate them.

After a mid-reply refusal fallback, the blocks before the fallback point are saved as their text only and the
`fallback` marker is dropped, as the API requires when a fallback turn is sent back.

Once a turn with tool calls is saved, its tool results are always saved too, even if the browser disconnects, because
a tool call without a result would make every later call in that conversation fail.

### Refusals, truncation and errors

| What happened | The user sees | Saved |
| --- | --- | --- |
| `stop_reason: refusal` (after any fallback) | "Claude declined to answer that..." | Nothing from that turn |
| `stop_reason: max_tokens` | "...too long and was cut off..." | Nothing from that turn |
| Rate limited (429), Anthropic 5xx, network error, bad API key | A short message for each; details in the API's log | Nothing from that turn |
| No `Anthropic:ApiKey` configured | "The API has no Anthropic API key..." | |
| 10 calls to Claude for one message | "...too many steps..." | The turns so far |

A refused or truncated turn isn't saved, because replaying a partial turn (perhaps with a tool call that has no
result) would break the conversation. The user's message stays. The Messages API combines consecutive user messages,
so it is read together with the user's next message.

## Rate limit

`POST /api/conversations/{id}/messages` is limited per user (the token's `sub`) by ASP.NET Core's rate limiter: a fixed
one-minute window of `Limits:ChatMessagesPerMinute` messages (default 10), no queueing. Over the limit it answers
**429** with a `Retry-After` header and a problem body titled `Too many messages`. Other endpoints aren't limited.

## Configuration

| Key | Default | |
| --- | --- | --- |
| `Anthropic:ApiKey` | none (secret) | Without it, chat replies with an error; the rest of the API works. |
| `Anthropic:Model` | `claude-sonnet-5-5` | |
| `Anthropic:Effort` | `low` | `low`, `medium`, `high`, `xhigh` or `max` |
| `Limits:ChatMessagesPerMinute` | `10` | per user |

## Testing

`FakeChatModel` (in the test fixtures) plays back scripted turns (text, tool calls, a stop reason, or a failure) and
records every request, so `ChatAgentTests` exercise the whole loop through the real endpoint, tools and database.
`AnthropicChatModelTests` check the SDK mapping against the exact request body the SDK would send (strict tools,
fallback, effort, cache control, and stored blocks sent back unchanged), and the fallback echo rule. No test calls
Anthropic. `AgentToolsTests.RealCatalog_StaysWithinStrictToolLimits` keeps the real catalog's tools within strict
mode's limits. `ChatAgentTests` also cover projects in chat: a project and a member proposed in one reply, another
user's project refused, and `list_my_resources` grouping by project.
